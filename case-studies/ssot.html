Project Context & Background

Why This Project Existed

In a rapidly scaling multi-product ecosystem serving web and mobile platforms, design and engineering teams were building in silos. Each product team maintained its own component library, color palette, and spacing system. When a brand refresh was announced, 4 separate teams had to update their UIs independently — resulting in inconsistent rollouts, missed brand guidelines, and weeks of duplicated effort. The need for a Single Source of Truth (SSOT) became critical.

The Problem Statement

Friction & Roadblocks Faced by Users

The core challenges were threefold: (1) Over 140 redundant button states and form variants existed across 4 product libraries, with no shared naming convention. (2) Color hexes were hardcoded directly into components rather than referencing design tokens, causing style drift whenever a designer tweaked a shade. (3) Developer handoff was manual — engineers received static Figma screenshots and had to eyeball spacing, shadow values, and border radii, leading to a 2–3 day lag per component implementation.

Research & Discovery

How We Listened to the User

I conducted a comprehensive design systems audit across all product teams:

▸Component Inventory Audit: Cataloged every button, input, modal, card, and table variant across 4 Figma files. Found 142 redundant components with inconsistent naming (e.g., "btn-primary", "Button/Main", "cta-blue", "primary-btn").
▸Developer Interview Sessions: Held 1-on-1 interviews with 6 frontend engineers to understand their token consumption workflow. Key finding: 78% of developers preferred CSS custom properties mapped 1:1 to design tokens rather than raw hex values.
▸WCAG AAA Contrast Analysis: Ran every color combination through contrast-ratio testing tools. Discovered 23 color pairings that failed AA compliance and 41 that failed AAA — particularly in dark mode surfaces.
▸Competitive Benchmarking: Studied IBM Carbon, Shopify Polaris, and Atlassian's design system architecture to identify best practices for token taxonomy and component API design.
Step-by-Step Architecture

The Design & Iteration Process

Discovery & Audit

Week 1–2

Cataloged 142 redundant components, mapped token consumption patterns across engineering teams, and established a naming convention standard based on the Design Tokens W3C specification.

Token Architecture

Week 2–3

Defined a 3-tier token hierarchy: Primitive tokens (raw values: colors, spacing, font sizes), Semantic tokens (purpose-based: surface-primary, text-secondary, border-subtle), and Component tokens (scoped: button-bg-primary, input-border-focus). Built all tokens as Figma Variables with light/dark mode sets.

Component Library Build

Week 3–6

Rebuilt 48 atomic components from scratch using Auto Layout 5.0 with responsive min/max constraints. Every component supports all interactive states: default, hover, active, focus-visible, disabled, loading, and error. Stress-tested with real content strings ranging from 2 to 200+ characters.

Accessibility & QA

Week 6–7

Validated every component against WCAG AAA standards. Built an accessibility testing matrix covering color contrast (minimum 7:1 for body text), touch target sizes (minimum 44×44px), focus indicator visibility, and screen reader label completeness.

Documentation & Handoff

Week 7–8

Created comprehensive documentation for each component: usage guidelines, do/don't examples, token mapping tables, and responsive behavior specifications. Built a developer handoff bridge mapping every Figma Variable to its CSS custom property and Tailwind utility equivalent.

Architectural Solution

Engineered for Usability & Precision

Architected the Single Source of Truth (SSOT) system utilizing Figma Variables for primitive and semantic tokens (colors, typography, radii, shadows). Created fluid responsive components in Auto Layout 5.0 with full interactive states (hover, active, focused, disabled). Established a 3-tier token hierarchy — Primitive → Semantic → Component — ensuring that a single token change propagates across the entire ecosystem without manual intervention.

Measured Outcome & Business Value

Quantitative & Qualitative Results

Reduced feature design turnaround by over 60% — what previously took 3 days per component now takes 4 hours using pre-built tokenized components. Eliminated visual regressions across frontend builds entirely. Established seamless 1:1 token alignment with Tailwind and React component libraries. Brand refresh rollouts that previously required 4 separate team sprints now deploy in a single coordinated update by changing token values at the primitive layer.

Retrospective & Honest Takeaways

What I Learned & What I'd Do Next

The biggest lesson was that a design system is a product, not a project. It requires ongoing governance, versioning, and stakeholder buy-in. The initial resistance from product teams ("our components work fine") dissolved once they experienced the speed of building with tokenized components. If I were to do it again, I would involve engineering even earlier in the token naming process — the naming convention alignment between design and code was the most debated and time-consuming decision.
